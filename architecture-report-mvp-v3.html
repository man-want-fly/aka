Schedule

105 个 Rust 指标 + 黄金用例验证本身就要 ≈26 人周（占总量一半）。加上引擎内核、数据层、前端与打包，总量 52 人周。14 周需要 3.7 FTE，不是 1.5 FTE。

Data

必须直说的一点：手册给的是「指标百科」，不是「规格说明书」。105 个指标里，78 个能直接从手册推出完整公式，19 个只有部分参数或需补默认值，8 个基本没有可复现定义（SCTR 打分权重、CTM 六框架、CMB、Special K、PMO 平滑阶数、RRG 归一化、Pring 系列、ITBM/ITVM/STO、Traffic Light）。这 27 个要么自定口径并在口径页标注「本产品定义」，要么不进首发。数量达标与「每个都可复现」是两件事，不能混为一谈。

另外两条判断：① 去掉 Python sidecar 之后，包体从 ≈150MB 降到 ≈30MB、冷启从 4s 降到 1.2s、公证从「主包 + 内嵌解释器 + 动态库」变成「单一签名」，这几项是净收益；代价是指标迭代速度变慢、Rust 指标生态薄，必须自建黄金用例体系。② 105 个指标对 MVP 是负资产而不是卖点——它把关键路径从「画图 + 数据」变成「数学正确性」，而后者用户看不见、验收却最严。

1.4 约束之间的真实冲突

C2 × C3 是这一版最贵的一处组合。「Rust 写」意味着没有 pandas-ta / TA-Lib 的现成函数可调，也没有 NumPy 向量化兜底；「105 个 + 按需」意味着每个指标都要能接受任意窗口、任意范围、任意数据版本，还要能被缓存与增量。两条叠起来，单个指标的成本从「0.3 天」变成「0.8~2 天」，且每个都要配黄金用例。这是工作量结论的直接来源，不是估算保守。

03

Rust 指标引擎：结构、契约与按需计算

这一节回答四个问题：代码怎么放、参数怎么描述、输入输出用什么形状、什么时候算以及算完放哪。

3.1 crate 与模块结构

单个 Cargo workspace，6 个 crate。核心原则是计算内核不依赖 IO、不依赖 Tauri、不认识数据库，这样它可以被单测、被 CLI 基准、被未来的服务端复用。

依赖方向严格单向：desktop → app-core → {indicator-core, data-store, data-provider}。indicator-core 不依赖 Arrow、不依赖 tokio、不依赖任何 provider。这条约束保证「换 provider、换存储、换 UI」都不碰指标代码。

3.2 参数类型系统

参数不是 HashMap<String, f64>。每个指标在注册表里声明参数规格，UI 直接由规格渲染控件，引擎用同一份规格校验——单一事实来源，避免「前端限制 2~200、后端崩在 0」。

pub enum ParamSpec { Int { key: &'static str, label: &'static str, min: i64, max: i64, default: i64, step: i64 }, Float { key: &'static str, label: &'static str, min: f64, max: f64, default: f64, step: f64, unit: Option<&'static str> }, Enum { key: &'static str, label: &'static str, variants: &'static [&'static str], default: &'static str }, Bool { key: &'static str, label: &'static str, default: bool }, } // 周期窗口 = Int + 语义标记，便于 UI 显示「周期」而非「整数」 pub struct Period { pub min: u32, pub max: u32, pub default: u32, pub ma_type: MaType } // 规范化：排序键 + 定点格式化 → 稳定哈希（跨构建、跨平台一致） pub fn params_hash(v: &BTreeMap<&'static str, ParamValue>) -> u64; pub struct Meta { pub id: &'static str, // "macd" pub name_zh: &'static str, // "指数平滑异同移动平均" pub category: Category, // Trend / Momentum / Volatility / Volume / Stat / Breadth pub params: &'static [ParamSpec], pub outputs: &'static [OutputSpec], pub warmup: fn(&Params) -> usize, // 首个有效值所需的根数 pub inputs: InputReq, // OHLCV / 需基准 / 需横截面 / 需复权因子 pub complexity: Complexity, // O(n) / O(n·k) / O(n log n) pub tolerance: Tolerance, // Abs(f64) / Rel(f64) —— 黄金用例断言用 pub spec_status: SpecStatus, // ManualComplete / Partial / ProductDefined(beta) pub engine_version: u16, // 公式变更即 +1，缓存 key 含此值 }

四类参数之外，还有两个「非参数但影响结果」的维度必须显式进入缓存 key：复权方式（none/qfq/hfq）与时间周期（日/周/月）。它们不是指标参数，但换一个就必须重算——这是最容易漏的缓存 bug 来源。

3.3 输入输出契约：内核用切片，边界用 Arrow

结论先说：计算内核吃切片（&[f64]），Arrow 只出现在边界（IPC 传输、Parquet 落盘）。理由不是「Arrow 不好」，而是这三条：

  • 数据类型单一。行情只有 f64 与 i64 时间戳，没有字符串/字典/嵌套列，Arrow 的列式优势在这个形状上退化成一个「等长的 f64 数组」。
  • 零拷贝本来就成立。Float64Array::values() 返回 &[f64]，直接喂给内核即可；中间再加一层 Arrow 只会多一次 validity bitmap 判断与 builder 开销。
  • 内核要保持无依赖。让 indicator-core 依赖 arrow，等于把「存储格式」泄漏进「数学库」，未来换格式要重编全部指标。
pub struct OhlcvView<'a> { pub open: &'a [f64], pub high: &'a [f64], pub low: &'a [f64], pub close: &'a [f64], pub volume: &'a [f64], // 股（统一单位后） pub amount: &'a [f64], // 元 pub ts: &'a [i64], // epoch 秒，用于对齐与去重校验 } // 边界适配：RecordBatch → 切片视图（不复制数据） impl<'a> OhlcvView<'a> { pub fn from_batch(b: &'a RecordBatch) -> Result<Self, ShapeError>; } // 输出：调用方预分配，避免每次计算反复分配 pub struct OutputBufs<'a> { pub bufs: &'a mut [Vec<f64>] } pub trait Indicator { const META: &'static Meta; fn calc(&self, v: &OhlcvView, span: Span, p: &Params, out: &mut OutputBufs) -> Result<(), CalcError>; }

NaN 语义：预热期、不可计算（除零、全零量、常数序列下的 %B）、停牌无数据，一律输出 f64::NAN，绝不补 0。前端渲染时跳过 NaN 段并用虚线断开——这条规则决定了「看起来没线」是可解释的，而不是 bug。

边界格式为什么
内核 ↔ 编排切片 + 预分配 Vec<f64>零拷贝、无依赖、可 benchmark
编排 ↔ 前端Arrow IPC 字节（<64KB 时退回 JSON）一次批量返回 3~8 条线，二进制省解析时间；小包用 JSON 便于调试
存储 ↔ 编排Parquet（按标的 + 年分区）只读所需列（OHLCV），压缩比 ~5x，mmap 友好
参数 ↔ 缓存规范化字符串 + FNV-1a u64跨进程/跨构建稳定；不用 DefaultHasher（不保证稳定）

3.4 增量与全量的统一：只允许一个入口

不设计两套算法。对外只有一个 calc(span)，内部按 from - warmup 向前多取一段，保证结果与全量计算在这个区间上逐位一致（同一内核，同一顺序，无并行归约）。

场景调用方式实际计算量一致性
首屏全量calc(0..n)n 根基准
追加一根calc(n-1..n)warmup + 1 根（如 EMA200 取 601 根）与全量逐位一致
缩放/平移不计算0（只重绘）—
改参数新 key，calc(0..n) 或可见窗口可见窗口 + warmup与全量一致（同参数）
流式白名单calc_step(state, bar)1 根需等价性测试（容差 0）

流式白名单只有 12 个：EMA、RSI、ATR、MACD、PPO、PVO、OBV、A/D、Chaikin、CMF（递推和）、TRIX、KAMA。它们的状态可以 O(1) 保存（前值 + 少量累加器）。其余指标一律走「前缀重算」——不是因为懒，而是因为两套实现必然分叉，而分叉在金融数值上是不可接受的维护成本。前缀重算的代价是固定的 warmup（典型 200~600 根），在 2,000 根可见窗口下只多 10~30% 计算量，换来「永不分叉」。

EMA 族的种子必须写进口径页：以首 N 根 SMA 作种子（TA-Lib 约定）还是以首根收盘价作种子（部分库约定），会导致前 2~3 个周期内出现 1e-3 级差异。手册没有规定，必须由本产品声明，并让黄金用例按同一约定生成。这是 105 个指标里最常见的「看起来都对、就是不一样」来源。

3.5 按需计算：一次请求如何变成一次计算

维度设计为什么这样
缓存 key(dataset_id, security, timeframe, adj_mode, indicator_id, params_hash, data_version, engine_version)少一项就会串数据。最容易漏的是 adj_mode 与 engine_version
缓存粒度按 (标的, 指标) 一条记录，内含各输出线；记录内记 last_ts同一标的多个指标共享读；尾部追加可判定
失效策略数据版本变化 → 该标的全逐出；复权因子变 → 全逐出；参数变 → 新 key（旧条目留给 LRU）保守优先：宁可多算一次，不可显示旧值
内存上限全局 256MB，单标的 32MB，单条记录 ≤4MB；超限按 LRU + 体积加权逐出2,000 根 × 3 线 × 8B ≈ 48KB/记录，可容 5,000 条
批量合并一次 IPC 携带全部指标；同 (标的,周期,复权) 只读一次行情；同 id 同参去重5 个指标 5 次调用会把 IPC 往返从 1 次变 5 次，首屏直接超预算
取消语义generation id 单调递增；旧请求返回时若 id 落后则丢弃结果，不写缓存改参数时用户连续输入，不能出现「后发先至」的旧曲线

3.7 正确性保障：黄金用例、容差与边界

Rust 没有成熟的 TA 指标库（ta / ta-rs / indicators 三个 crate 加起来覆盖不到 40 个，且口径不一致），所以正确性不能靠「参考某个库」，只能靠「自己建立参考系」。

三层验证

层做什么覆盖失败即阻塞
L1 黄金用例离线用 TA-Lib / pandas-ta / TradingView 导出参考序列为 JSON，提交进仓库；Rust 测试逐点比对78 个「✓完整」指标 × 5 组输入是
L2 恒等式与结构不依赖外部参考的数学性质：MACD 柱 = DIF−DEA；%B 与 BB 带宽互补；Aroon Up+Down 关系；RSI ∈ [0,100]；OBV 单调性全部 105 个是
L3 边界与鲁棒7 类病态输入（见下）不 panic、不产生 Inf、NaN 位置正确全部 105 个是
输入组构造验证什么
A 趋势线性上涨 + 轻微噪声，2,000 根趋势类指标方向与量级
B 周期正弦 + 噪声，周期 20/50 混合摆动类指标的极值与滞后
C 常数全序列同一价格、同一成交量σ=0 → %B 必须 NaN；RSI 定义需明确（0/0→50 还是 NaN）
D 零量价格为真、成交量全 0MFI / CMF / EMV / OBV / 量比 的显式定义
E 跳空涨停连续 3 个 +10% 一字板，H=L=CTR、ATR、KDJ 的除零与分母退化

3.9 前端怎么调：Tauri command，不用本地 HTTP

选 Tauri command（推荐）

  • 无 sidecar，就不需要端口、不需要 CORS、不需要本地鉴权
  • 无进程间握手与 health check，冷启动路径更短
  • 参数与返回值走类型化 DTO，编译期就能发现字段错配
  • 大载荷可用 tauri::ipc::Response 直接回二进制，避开 JSON 解析
  • 取消可用 generation id + 前端丢弃，无需断开连接

不选本地 HTTP

  • 为一个单机单用户应用引入 HTTP 栈，只增加攻击面
  • 端口冲突、防火墙弹窗、随机端口发现都要额外处理
  • 需要另建一层错误码/鉴权/超时约定，收益为零
  • 未来若要做服务端复用，app-core 本身就是库，换壳即可
// 前端（TS）— 一次批量取 5 个指标 await invoke<ArrayBuffer>("calc_indicators", { req: { security: "000001.SZ", timeframe: "D", adj: "qfq", from: 0, to: 2000, generation: 17, batch: [ { id: "macd", params: { fast: 12, slow: 26, signal: 9 } }, { id: "rsi", params: { period: 9, ma_type: "wilder" } }, ] } }); // 后端错误（Rust）→ 前端表单错误（TS） // { code: "PARAM_OUT_OF_RANGE", indicator: "rsi", param: "period", // min: 2, max: 200, got: 1, message: "周期需在 2~200 之间" }

错误分三类，回传语义不同：可纠正（参数越界、数据不足）→ 结构化字段，前端直接标红并给出可用范围；可重试（数据文件被占用、临时 IO 错误）→ 带 retryable: true 与建议等待；不可恢复（注册表 id 不存在、内核 panic 被捕获）→ 上报诊断包并提示重启。指标计算不 panic：所有 unwrap 在 indicator-core 内被 lint 禁止，除零走 NaN 分支。

4.4 存储：为什么把 DuckDB 换掉

v2 用 DuckDB 做分析库，在「预计算 + 横截面 SQL」的场景下是对的。v3 的场景变了：按需计算、只读单标的窗口、无复杂 SQL。此时 DuckDB 的代价（静态链接约 +35MB、需 C++ 构建链、启动打开 catalog 的延迟）开始大于收益。

DuckDB（v2）≈+35MB≈15ms强（SQL）延后 横截面需求出现且数据到全市场时再引入

一句话：无账户无支付把部署压到「一个静态桶 + 两份清单」，但同时也把「产品是否被使用」变成盲区。MVP 可以接受这个盲区，因为它的目标不是增长，而是用 10 个人验证「指标可信 + 看图顺手」。如果后续要做增长，第一个要补的不是支付，而是可选遥测。

6.5 仍然开放的问题

  1. 105 个是否首发全上，还是首发 48 个 + 后续版本补？这是唯一能改变时间线的问题，必须由产品拍板。
  2. 广度类 16 个在 mock 下是否有意义：样本 300 只算出的「腾落线」是否只会误导用户？是否应标记为「演示」而非可用指标？
  3. 参数范围谁定：手册大多只给默认值，不给上下界。范围过宽会让用户算出无意义结果，过窄会限制研究。
  4. 口径页写到什么深度：公式 + 参数 + A 股口径 + 陷阱 + 用例来源，105 份按每份 200~400 字，约 3 万字。
  5. 「指标组合」是否要能保存：多 id + 多参数 + 主副图位置的组合，是 v2「收藏」的升级版，工作量 +1 人周。
  6. 复权默认口径：前复权锚点选「最新交易日」还是「上市首日」？前者会随新数据整体平移，影响画线锚点与缓存失效。
  7. mock 的「真实感」由谁验收：涨跌停比例、停牌比例、除权频率，这些统计特征需要有对照基准，否则无法判定。
  8. 更新通道国内可达性：GitHub Releases 在国内不稳定，首发是否直接上对象存储 + CDN（成本略增）。
  9. 诊断包隐私边界：是否包含用户自选代码？包含则可能泄露持仓偏好，不包含则难以定位问题。
  10. 29 万根基准是否保留：MVP 无分钟线，这个基准只服务架构验证。是否值得为它投入 4 人周的性能工作？
