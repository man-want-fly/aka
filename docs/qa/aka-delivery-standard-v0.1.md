# AKA 代码交付规范 v0.1

> 生效：2026-11-08。对 dev A、dev B、BA、QA、TL 同时生效，不是建议。
> 依据：`docs/qa/aka-card-decision-audit-v0.1.md` 制度第 1–35 条。本规范是**执行口径的汇总与收敛**，与制度冲突时以本规范为准，并在当周审计里回写制度。
> 机器判定优先：能进 `verify:*` / CI 的，必须有脚本与反例；不能机械化的，写成评审清单，并在工单对应步骤挂勾。

---

## 1. 一张卡「完成」的判定

### 1.1 四件齐

一张卡只有同时满足下面四件才算完成（`已交付`）：

| 件 | 判据 | 谁产出 |
| --- | --- | --- |
| 代码 | 已合入 `main`；合并后 tip 的 CI 绿；`tsc --noEmit`、build、cargo test、golden 全过 | dev |
| 证据 | `docs/qa/evidence/` 有 dump + meta；`verify:evidence` failed=0；`dump.commit` 等于或祖先于签字 commit；运行层证据满足第 19/23/25/28 条 | BA |
| 签字 | gate-log 该行 `gate_c=PASS`、`sign_commit` 40 位、`sign_scope` 写明范围；`aka-ci-sign-ledger` 有对应绿 run | TL |
| 台账 | 完成台账有该卡行，状态与 gate-log 一致，计数口径见 §8 | BA |

### 1.2 状态词表（只许用这些，不造新词）

| 状态 | 含义 | 判定 |
| --- | --- | --- |
| `未开始` | 未派工或未动 | 台账行存在即可 |
| `待签` | 代码 + 证据齐，缺签字 | 机器：gate-log 无 `sign_commit` 且 `gate_c=PASS`；评审确认四件里只缺签字 |
| `Blocked` | 依赖未交付，整卡不可推进 | 必须写 `blocker`，且 `skipped=false` |
| `Blocked-AC` | 部分 AC 可判且 PASS，另有 AC/补记不可判 | 第 33 条：卡级取最严；`sign_scope` 必须限定到具体 AC |
| `条件交付` | 卡已签，但带明确条件（如仅某 AC、仅某环境） | gate-log note 必须有 `[条件签]` 或条件文本；条件未满足前不得升 `已交付` |
| `已交付` | 四件齐 | 机器：`verify:delivery` 校验「已交付 ⇒ sign_commit 非空」（存量白名单见 §1.3） |
| `已结项` | 并入宿主卡或不再单独交付 | gate-log 行 + 台账行；引用宿主卡号 |

- **不合格判定**：出现词表外状态 → `verify:gate-log` 直接红；`已交付` 但无签字 → `verify:delivery` 红（§1.3 白名单除外）。
- **未合并 / 未取证不得称完成**：代码只在分支/worktree、或证据未在合并后 commit 上重取，一律记 `待签`（代码已完成）或 `待开工`（未动），不得写「已完成」；`Blocked` 只用于外部依赖未交付。
- **反例**：`W-92` 曾被记成「已完成」但既无取证也无签字，属状态词滥用，已按词表改回；dev2 上的 `P06`/`P07` 同理，代码完成不等于卡完成。

### 1.3 存量豁免（只减不增）

`verify:delivery` 内置 `LEGACY_NO_SIGN`：`S-01.01-01`、`S-01.01-02`、`S-01.01-03`、`S-02.02-01`、`S-02.02-02`、`S-02.06-02`、`S-02.07-01`、`S-02.07-02`、`S-03.04-01`、`S-06.01-02`（截止 2026-11-22）。名单只许删、不许加；新增卡无签字即红。

## 2. 提交规范

### 2.1 分支 / worktree

- 主树 `main` 只做合并、签字、台账；开发一律在独立 worktree（`AKA-w91` 之类）+ 分支，分支名 `w<工单号>/<主题>`。
- 同一时刻同一 worktree 只允许一个执行人写入。**取证窗口内禁止任何提交**（第 26 条），窗口开始前必须 `git status` 干净。

### 2.2 提交信息格式（机器判定）

```
<type>(<scope>): <中文摘要>

- 改了什么、为什么
- 连带修正：<文件 L行> 原值 → 新值
- Sign-Invalidates: none | <卡号/行>
```

- `type` ∈ `feat|fix|docs|sign|evidence|merge|refactor|test|chore|chore`；`scope` 小写中划线。
- **`Sign-Invalidates:` 必填**：只要本次 diff 触碰 `docs/qa/aka-card-gate-log-v0.1.csv`、`docs/qa/evidence/` 或已签卡的卡面，必须写明失效范围；无失效写 `none`。
- **「连带修正：文件 L行 原值→新值」必填**：改常量、改派生口径、改卡面数字时，逐条列出旧值和新值；只写「已修正」视为未交付。
- **不合格判定**：`verify:delivery` 校验 HEAD 提交信息（subject 格式 + 触碰签字产物时的 trailer）；CI 红。合并提交跳过 trailer 检查，但合并提交正文必须列出被合并的 commit。

### 2.3 索引归属（`4f44b08` 事故）

- 提交前必须核对：`git status --porcelain` 与 `git diff --cached --name-only`，确认索引里**没有别人的暂存内容**。同树两方作业时，只 `git add <自己的文件>`，禁止 `git add -A` / `git add .`。
- **不合格判定**：评审。TL 在合并前 `git show --stat <commit>` 与实际交付清单逐项对照；出现「说明里只有 6 个文件、实际包含别人门禁改动」即判不合格，需在审计里如实记录（`4f44b08` 已记录）。

### 2.4 历史纪律

- 禁止 `git commit --amend`、`git push --force`、rebase 已推分支、改写已推历史。
- **不合格判定**：评审 + `gh api` 查询 force push 记录；一旦发生，该分支的绿 run 与签字全部作废，按 §1 重新取证签字。

## 3. 自测的最低要求

### 3.1 dev 交付前必须全过

`tsc --noEmit`、`vite build`（`NODE_ENV=development`）、`cargo test`、golden、以及仓库内全部 `npm run verify:*`（含 selftest）。数字写进交付说明，不写「已跑」。

### 3.2 不得自跑运行层取证

运行层 GUI 取证只能由 BA 走 `evidence-run.sh`（第 23 条）。dev 可以跑单测/组件测试，但**不得自己出 dump、不得把本地截图当证据**。

### 3.3 取证链路

- 唯一入口 `app/scripts/evidence-run.sh <suite>`；路径只从 `evidence-layout.json` 读（第 27 条）。
- 窗口只置前一次，dump 记 `activateAttempts`（第 23 条 d）；失败/超时产物必须落 `docs/qa/raw/`（第 31 条 / W-94）。
- **不合格判定**：`verify:evidence` 校验路径、env 五项、meta 同源、`activateAttempts`、失败记录字段；缺一红。人工步骤取证（`open /tmp/*.command`）一律不认。

## 4. 判据与反例

### 4.1 什么必须配反例

任何新增或修改的：派生逻辑、映射、分区、计数、选择器、汇总口径，**必须同提交**给出「会让它错」的反例，并做变异验证：把实现退回错误形态，反例必须从「红」变「绿」；改回实现必须变红。

### 4.2 汇总口径

顶层汇总必须覆盖所有 `verification` 子块（第 30 条），`ok = checksOk && verificationOk`；任一子块 `ok=false` 顶层即 false。禁止用 `checks[]` 的全绿掩盖子块红。

### 4.3 工具与检查器

- 检查器不算交付，除非：有反例、有 selftest、进 CI、且**工具开发者不得做该工具的取证执行人**（§6）。
- `dom-contracts.json` 为选择器唯一清单（第 32 条）；新增 `data-*` 不登记即红。

### 4.4 不合格判定

缺反例 = 未交付；反例不能变红 = 检查器无效，工单退回；变异后反例仍红 = 反例与被测逻辑无关，退回。

## 5. 合并前置

1. `main` 工作区干净、已 push、CI 在 tip 上跑过。
2. 对待并入 diff 先跑 `npm run verify:sign-impact -- --staged` 预演（不是合并后再补）。
3. 共用文件（`app/bench`、`app/manifest/indicators.json`、`app/scripts/dom-contracts.json`）**先合先定基线**；后合一方按基线重生成，禁止各改一处。
4. 合并后必须重跑 `verify:evidence`、`verify:dom-contracts`、`verify:gate-log`、`verify:sign`；两边各自的绿拼起来可能是红的。
5. **不合格判定**：`verify:sign-impact` 白名单外命中非 0、或合并后任一 `verify:*` 红，即不得合并；已合并的按第 21 条处理。

## 6. 审查边界

| 角色 | 可以做 | 不得做 |
| --- | --- | --- |
| dev | 写实现、跑自测、报数字 | 自证交付、自出运行层证据、改台账/签字 |
| BA | 运行层取证、写完成台账 | 改卡面、改门禁判据、给自己取证结论签字 |
| QA | 反向验证、构造反例、审查证据有效性 | 做被审卡片的实现 |
| TL | 裁口径、签字、合并、改制度 | 替 dev 改代码后自己签；工具开发者兼任取证执行人 |
| 工具开发者 | 写检查器与反例 | 用自己写的检查器为自证取证（必须换人执行） |

- **不合格判定**：评审。签字行 `signed_by` 与实际执行人冲突、或同一人同时出现在「实现」与「取证执行」两栏，签字作废。

## 7. 状态同步义务

- `docs/qa/aka-card-workorder-v0.1.md` §0.0 是唯一共享状态表。**取卡、开工、报完成、停线当天写入**；别人贴单前先看它。
- 进行中必须写分支/worktree；停线必须写原因与恢复条件。
- 每天至少一次由 TL 对表；批次边界统一复核（第 14 条）。
- **不合格判定**：`verify:delivery` 校验状态表（重复编号、非法状态、进行中缺分支、表内编号无对应工单标题）；缺一项红。人工判定：聊天里说「在做了」但表里没有 → 视为未开工。

## 8. 汇报节奏

### 8.1 必须立刻报

- 取证失败、崩溃、超时、零 dump；
- 阻塞（依赖未交付、环境不可用、权限缺失）；
- 需要口径裁定（状态词、卡级取严、签不签）；
- 发现已签证据被推翻（实质反证）。

### 8.2 可以攒到批次边界

- 交付进度、下一批计划、非阻断 WARN、时延观察值（如 `b2Render 291ms`）。

### 8.3 汇报格式

- 结论 + 数字 + 口径 + 证据路径/commit。禁止「基本可签」「建议放行」「除某条待定」。
- 计数必须双口径（第 22 条）：卡数/人日百分比分开写。
- **不合格判定**：评审。缺口径、缺 commit、用模糊措辞，汇报退回重写。
