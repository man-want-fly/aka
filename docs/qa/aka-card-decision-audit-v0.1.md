### 4.5 G8：引用存在性（W-03 空门禁的教训）

**真实案例**：W-03 让卡引用 `npm run verify:docs` 与 `app/scripts/verify_indicator_docs.mjs`，两者在仓库里都不存在。卡改了、门禁没建，构建照常绿——这比没有门禁更糟，因为它制造「已检查」的错觉。

**G1–G7 为什么拦不住**：G1 管裁定，G2 管 AC 可复算，G3/G6/G7 管内容完整性，G5 管常量。它们都默认「引用的检查已经存在」，没有一条检查「引用本身是否指向真实文件/命令」。所以必须单列 G8。

**G8 可自动检查**：是。最小实现：

1. 抽取：正则扫卡与工单中的 `npm run <script>`、`node scripts/<file>.mjs`、`app/**`、`docs/**`、`tests/**` 路径；
2. 解析：`npm run x` → `package.json.scripts.x` 必须存在，且其命令里引用的 `scripts/<file>` 也必须存在；
3. 校验：相对仓库根的路径 `existsSync`；
4. 例外：尚未创建的产物必须显式标记 `planned: <owner> <date>`，否则 FAIL；标记需定期清理，防止永久豁免。

**豁免条目的形态（已确认，适用于 G5 白名单与 G8 `planned` 标记）**：豁免必须绑定**原文片段**且可失效——

- 每条 = `pattern + 文件 + 行号 + ≥20 字原文片段 + 放行理由`；`line` 仅供人工核对（卡片并发编辑会平移），**匹配条件是文件 + 原文片段**；
- 命中失败（原文被改写、片段被删、pattern 改名）→ 报 **STALE** 并 **exit 1**，迫使放行者重新逐条确认；
- 禁止「行里含 V1 就豁免」这类规则免疫——那样任何文档随手加个 V1 就永久免疫；
- 当前 `sector-12` 两条即以该形态放行（`aka-story-cards-v0.1.md` 的降级陈述与生成器禁令），baseline 保持 0 条。

**放在哪道门**：**Gate A（自动、确定性）**，不进 Gate B。理由：存在性不需要技术判断，TL 签只能补漏不能替代机器。Gate B 仍保留一条人工确认：「引用的检查语义是否覆盖卡内承诺」——文件存在 ≠ 检查有效（W-03 的脚本即使存在，也必须按 8 项检查实现才算数）。

**失败输出**：

```
S-03.03-03: 引用了 npm run verify:docs，但 package.json 无此 script
建议：新建 app/scripts/verify_indicator_docs.mjs 并接线，或改为 planned: dev 2026-11-14
```

**落地顺序**：先写 `app/scripts/verify_refs.mjs`，与 `verify:constants` 同组挂到 `prebuild`/CI；存量先 `--report` 清一遍。W-03 脚本落地前，`S-03.03-03` 保持 `Blocked-AC`，不得因为「卡面已改」就签 Gate B。

### 4.7 签字绑版本、分歧复判与追加裁定（2026-11-07）

#### 4.7.1 七条制度（立即生效）

1. **Gate B 签字必须绑定 commit**：`gate-log` 增加 `sign_commit`、`sign_scope`（全卡复核 / diff 复核）。卡片在被签 commit 之后有任何改动，签字即失效，必须按 diff 复核后重签；**未绑定 commit 的签字一律不认**。
2. **Gate A / Gate B / Gate C 任一列不 PASS 即不放行**；空白等同未 PASS，不得口头放行。
3. **两列结论不一致时**，各方先写依据（卡号 + 行号 + 原文），再由 **PM 改判**；任一方不得单方面放开。
4. **报告与台账禁止「可签，除某条待定」「基本可签」「建议放行」**；留一个待定即视为不可签。原「勘误不阻断」一律作废——AC 数字与字段表/文案不一致就是假断言。
5. **批量改完 → 统一重签**：卡片修订按批次一次落完后再集中复核、集中签字，**不许「一卡一改一签」逐张重签**。同一卡的多处修订必须一次改到位再进 diff 复核；否则每次改卡都使既有签字失效，时间会全部耗在重签上。
6. **`gate-log` 是签字唯一权威**：BA 台账只保留完成度与版本、结论写「见 gate-log」；Gate C 由 TL 录入 `gate-log` 并在 `gate_c_source` 标「BA <commit>」，不替 BA 下结论。所有「可放行/不可放行」表述一律以 `gate-log` 的 Gate A/B/C 三列为准，禁止凭印象或引用第二份台账。
7. **人力/规模类数字单一源**：`aka-story-cards-v0.1.md` §1「卡片总览表」是唯一权威（22 Feature 明细 + 8 个 Epic 概算 + 总合计）；逐卡人日只在该卡「规模估算」段出现一次。其它位置——本文件 §10、完成台账、planning、审计报告、架构文档——**只写「见卡文件 §1 总览表」**，不再复制具体数值；派生量（人周、2 人并行 0.75 折算、15% 缓冲）只允许在该文件第 10 节按公式出现一次，并注明「由 §1 派生」。索引 CSV 的 `estimate_pd` 是唯一允许保留的机器副本（脚本与排期要读），投影自 §1：重估时**先改表、再统一重生成索引**，禁止两处手工改数；一致性校验器落地前，同一次提交内人工核对并把结果记入台账变更记录。**历史记录豁免**：`changelog`、旧立卡口径（如 W-27 前的 `18.0`、`208.9/41.8/75.4/55.7/240.2` 链）保留原值、**不得改写**；如需说明只加「旧口径，已按 §1 重估」，不回填新数。违反单一源、靠全文档扫替换的批量派生改动（W-27 式 21 处）记为文档缺陷。
8. **报可放行必须带签字版本**：任何「可放行」清单不得只给卡号；格式固定为 `卡号 | A/B/C | sign_commit | 是否漂移`。不带 `sign_commit` 的放行表述无效；「是否漂移」须相对当前 HEAD 核对，结论只能是「否」或「是（已重签 X）」二选一。
