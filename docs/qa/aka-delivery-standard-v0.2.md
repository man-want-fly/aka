## 1. 一张卡「完成」的判定

### 1.1 四件齐

一张卡只有同时满足下面四件才算完成（`已交付`）：

| 件 | 判据 | 谁产出 |
| --- | --- | --- |
| 代码 | 已合入 `main`；合并后 tip 的 CI 绿；`tsc --noEmit`、build、cargo test、golden 全过 | dev |
| 证据 | `docs/qa/evidence/` 有 dump + meta；`verify:evidence` failed=0；`dump.commit` 等于或祖先于签字 commit；运行层证据满足第 19/23/25/28 条 | BA |
| 签字 | gate-log 该行 `gate_c=PASS`、`sign_commit` 40 位、`sign_scope` 写明范围；`aka-ci-sign-ledger` 有对应绿 run | TL |
| 台账 | 完成台账有该卡行，状态与 gate-log 一致，计数口径见 §8 | BA |

### 1.2 状态词表（只许用这些，不造新词）

| 状态 | 含义 | 判定 |
| --- | --- | --- |
| `未开始` | 未派工或未动 | 台账行存在即可 |
| `待签` | 代码 + 证据齐，缺签字 | 机器：gate-log 无 `sign_commit` 且 `gate_c=PASS`；评审确认四件里只缺签字 |
| `Blocked` | 依赖未交付，整卡不可推进 | 必须写 `blocker`，且 `skipped=false` |
| `Blocked-AC` | 部分 AC 可判且 PASS，另有 AC/补记不可判 | 第 33 条：卡级取最严；`sign_scope` 必须限定到具体 AC |
| `条件交付` | 卡已签，但带明确条件（如仅某 AC、仅某环境） | gate-log note 必须有 `[条件签]` 或条件文本；条件未满足前不得升 `已交付` |
| `已交付` | 四件齐 | 机器：`verify:delivery` 校验「已交付 ⇒ sign_commit 非空」（存量白名单见 §1.3） |
| `已结项` | 并入宿主卡或不再单独交付 | gate-log 行 + 台账行；引用宿主卡号 |

- **不合格判定**：出现词表外状态 → `verify:gate-log` 直接红；`已交付` 但无签字 → `verify:delivery` 红（§1.3 白名单除外）。
- **未合并 / 未取证不得称完成**：代码只在分支/worktree、或证据未在合并后 commit 上重取，一律记 `待签`（代码已完成）或 `待开工`（未动），不得写「已完成」；`Blocked` 只用于外部依赖未交付。
- **反例**：`W-92` 曾被记成「已完成」但既无取证也无签字，属状态词滥用，已按词表改回；dev2 上的 `P06`/`P07` 同理，代码完成不等于卡完成。

## 2. 提交规范

### 2.1 分支 / worktree

- 主树 `main` 只做合并、签字、台账；开发一律在独立 worktree（`AKA-w91` 之类）+ 分支，分支名 `w<工单号>/<主题>`。
- 同一时刻同一 worktree 只允许一个执行人写入。**取证期间禁止任何提交**（第 26 条）——即该卡从采集证据到合并完成的这一段；采集前必须 `git status` 干净。

### 2.2 提交信息格式（机器判定）

```
<type>(<scope>): <中文摘要>

- 改了什么、为什么
- 连带修正：<文件 L行> 原值 → 新值
- Sign-Invalidates: none | <卡号/行>
```

- `type` ∈ `feat|fix|docs|sign|evidence|merge|refactor|test|perf|chore`；`scope` 小写中划线。`perf` 用于性能口径/判据类提交（2026-11-08 修订：`fbd4a28` 因枚举缺 `perf` 被误判红，属枚举缺口而非笔误）。
- **`Sign-Invalidates:` 必填**：只要本次 diff 触碰 `docs/qa/aka-card-gate-log-v0.1.csv`、`docs/qa/evidence/` 或已签卡的卡面，必须写明失效范围；无失效写 `none`。
- **「连带修正：文件 L行 原值→新值」必填**：改常量、改派生口径、改卡面数字时，逐条列出旧值和新值；只写「已修正」视为未交付。
- **不合格判定**：`verify:delivery` 校验 HEAD 提交信息（subject 格式 + 触碰签字产物时的 trailer）；CI 红。合并提交跳过 trailer 检查，但合并提交正文必须列出被合并的 commit。

### 2.3 索引归属（`4f44b08` 事故）

- 提交前必须核对：`git status --porcelain` 与 `git diff --cached --name-only`，确认索引里**没有别人的暂存内容**。同树两方作业时，只 `git add <自己的文件>`，禁止 `git add -A` / `git add .`。
- **不合格判定**：评审。TL 在合并前 `git show --stat <commit>` 与实际交付清单逐项对照；出现「说明里只有 6 个文件、实际包含别人门禁改动」即判不合格，需在审计里如实记录（`4f44b08` 已记录）。

### 2.4 历史纪律

- 禁止 `git commit --amend`、`git push --force`、rebase 已推分支、改写已推历史。
- **不合格判定**：评审 + `gh api` 查询 force push 记录；一旦发生，该分支的绿 run 与签字全部作废，按 §1 重新取证签字。

## 3. 自测的最低要求

### 3.1 dev 交付前必须全过

`tsc --noEmit`、`vite build`（`NODE_ENV=development`）、`cargo test`、golden、以及仓库内全部 `npm run verify:*`（含 selftest）。数字写进交付说明，不写「已跑」。

### 3.2 不得自跑运行层取证

运行层 GUI 取证只能由 BA 走 `evidence-run.sh`（第 23 条）。dev 可以跑单测/组件测试，但**不得自己出 dump、不得把本地截图当证据**。

- **`--check` 同归 BA**：`evidence-run.sh` 的任何模式（含 `--check` 预检）都只能由 BA 执行；dev 不得以「只验环境」为由运行。dev B 在下达禁令前的一次 `s080202 --check` 按「边界内例外、无产物」记录，不作违规，也不作自测结论（审计 §4.7.83）。

- **判定人与时点**：TL，签字前。依据三样：`meta.command` / `buildMode` / `runAt`、`evidence-run.sh` 的终端记录、BA 在 §0.0 该行的「取证执行人：BA」回执。
- **机器边界**：`verify:evidence` 不判断执行人身份（身份不可从 dump 自证，强判会制造假阳性）；它只保证 dump 与 meta 同源、路径与 env 合法。执行人是否合规由 TL 在签字时核对，核对结论写进 `aka-ci-sign-ledger` 的 `note`（`executor=BA`）。
- **不合格判定**：三样依据缺一、或实现者与取证执行人同一人 → 拒签；已签的按 §6 作废，证据退回 `docs/qa/raw/`，不算证据份数。
- **变异记录的分工**（第 29 条）：实现者（dev）只提供「变异补丁 + 回退命令 + 期望红的哪条 check」；实测由 BA 在该卡取证时执行（先绿 → 打补丁 → 必须红 → 回退 → 复绿）。两段记录都出自 BA 手，提供者与执行者不得同一人。

### 3.3 取证链路

- 唯一入口 `app/scripts/evidence-run.sh <suite>`；路径只从 `evidence-layout.json` 读（第 27 条）。
- 窗口只置前一次，dump 记 `activateAttempts`（第 23 条 d）；失败/超时产物必须落 `docs/qa/raw/`（第 31 条 / W-94）。
- **不合格判定**：`verify:evidence` 校验路径、env 五项、meta 同源、`activateAttempts`、失败记录字段；缺一红。人工步骤取证（`open /tmp/*.command`）一律不认。
- **触发类必须声明**：证据说明写 `trigger=real`（真实磁盘/目录/文件/数据触发）或 `trigger=injected`（`--dataset-fault=` / `--corrupt-*` 注入）。`injected` 只支撑「给定错误类时的 UI、动作可用性、写禁、无堆栈、恢复流程」类 AC；AC 的 Given 明确要求真实触发（如「删除 `data/sim` 目录」「篡改真实文件 sha256」）时，`injected` 不算该 AC 通过。
  - 分卡判法：真实触发类 AC 记 `Blocked-AC`，`blocker=磁盘数据集未接入`；行为类 AC 可签，但 gate-log 记 `条件交付`、note 写 `[条件签] trigger=injected`，`sign_scope` 不含真实触发类 AC。
  - **解除条件**：磁盘数据集接入后补真实触发证据，条件签才可升 `已交付`；只重取真实触发类 AC，既有注入类证据按第 34 条不追溯（实现被改动触碰的除外）。

### 3.4 证据 check 的 `ac` 字段语义

- `ac` **只承载卡面 AC token**：`AC-\d{2}\.\d{2}-\d{2}`，补号必须全角 `（补N）`，与卡面逐字相同。
- 任何限定语（`W/M`、`UI 无障碍`、`数据层`、`渲染层`、备注）一律进 `detail`，不得进 `ac`。
- **一个 check 只对应一个 token**；一条 AC 的多个补号必须拆成多条 check，不得用 `补2/补4` 这种合并写法。
- **禁止为兼容历史写法扩正则**去允许后缀或半角括号：QA 的「卡面 AC → check 覆盖闭合」检查要用 `ac` 做集合比较，一旦允许自由文本，该检查即失效。
- **不合格判定**：`ac` 不是合法 token、或一个 check 挂多个 token → `verify:ac-token` 红，阻断合并。

### 3.5 数字口径变更：历史数字只标注、不覆盖

- 判据/check 数、覆盖数、份数、人日等口径变化时，**旧数字不删改**，保留并标「（基线）」，同时给出新数字「（现口径）」。
- 例：`s080202` 补 `layer` 后由 6 条变 8 条，`gate-log` 记「原 6 条（基线）/ 现 8 条：render 6 + runtime 2」，不把 6 抹成 8。
- 同一处出现合计与分项时**必须相等**：`render 6 + runtime 2 + data 2 = 10`；分项写不全就不要写合计。
- 禁止同一句并列两个互斥数字（`6/6` 与 `8 条`、`44/105` 与 `49/105`）；冲突时以 `gate-log` 与取证产物为准，另一处标「已作废（基线）」。
- 口径变更须在同一批次内同步所有引用点（台账、工单、审计、交付说明），不得留两份数字。
- **不合格判定**：同一口径在仓内出现两个互不标注的数字 → 文档门禁不合格，按 `verify:docs` 复核处理。

### 3.6 AC 状态值必须可达

- **AC 里每个状态值必须有至少一条可达路径，并标注路径类型**：正常进入、注入（夹具/开关）、或「仅异常环境」。
- **没有可达路径的状态值视为死 AC，不得签字。**
- 理由只有一句：**无法到达的状态不能被验收，只能被假装验收。**
- 取舍顺序：**与既有注入模式同构 > 新增核心分支 > 改写 AC**。改写 AC 只能改措辞使其与产品要求一致，**不得改成实现恰好能过的样子**；错误态优先靠 debug-only 注入进入。
- **不合格判定**：AC 断言的状态在生产代码中不可达，且无夹具、无注入、无「仅异常环境」标注 → 该卡不得签字；已签的按第 25 条回退为「待验收」。
- 落地检查：新增/修改 AC 时必须给出「该状态如何进入」的一行说明（正常入口 / 注入开关或夹具名 / 异常环境标注），随卡面提交。
- **批检**：定期扫全卡「状态值 → 可达路径」，输出死 AC 清单；发现新的死 AC 单独开卡，不得顺手改产品。

### 3.7 计时窗口不得包含取证/诊断自身开销

- **计时窗口内不得包含取证、诊断、哈希收尾等仪器自身的开销**；仪器开销必须移出窗口，或改为无分配增量计算。
- 理由：判据一旦把仪器算进被测对象，数字就跟着机器负载漂。**这种判据不是「永远不红」，是「随机红」——同样不能用。**
- 反例要求：把仪器开销移回计时窗口后，该性能 check **必须变红**；否则说明窗口边界没有被真正测到。
- 引用限制：含仪器开销的既有数字**不得跨批次比较或折算**；引用时必须带「含哈希/仪器开销，非纯产品耗时」的限定，且不得据此调整阈值。
- **不合格判定**：性能类 check 的计时窗口含仪器开销且未标注 → 该卡不得签字。

## 4. 判据与反例

### 4.1 什么必须配反例

任何新增或修改的：派生逻辑、映射、分区、计数、选择器、汇总口径，**必须同提交**给出「会让它错」的反例，并做变异验证：把实现退回错误形态，反例必须从「红」变「绿」；改回实现必须变红。

- **手法提供者 = 实现者（dev）**：交变异补丁、回退命令、期望红的 check 名称。
- **实测执行者 = BA**（运行层）或 QA（单元层）：在该卡取证时执行「绿 → 补丁 → 红 → 回退 → 复绿」，记录两人姓名进签字 `note`。
- **不合格判定**：提供者与执行者同一人、缺回退命令、期望红的 check 未写、或实测只有红没有复绿 → 视为未交付，不签。

### 4.5 门禁假阳性单独取证（第 37 条）

门禁不仅要证明「该红能红」，还要证明「不该红的不会红」。每一次门禁修改，必须同时交：

1. **假阳性样本**：真实产品功能被误杀的现场（卡号、功能、门禁规则、误杀输出）；
2. **修复**：最小改动 + 为什么不是放松门禁；
3. **回归反例**：修复后该功能放行、原来的坏人路径仍红（两个反例都要有）。

- **判定人与时点**：TL，门禁合并前；记录进审计对应 §4.7.x。
- **反例（已发生）**：W-49 门禁把 `AKA_BUILD_NO`（W-28 构建元数据）当诊断标记、把 release「导出诊断包」写盘当调试写盘，误杀 `208ce8f`。修复采用「标记收窄 + 用户导出白名单 + cfg 化」，并保留 `AKA_DIAG*` 与调试写盘的反例；不是简单放行。
- **不合格判定**：只写「修好了」、没有假阳性样本、或修复后原坏人路径不再红 → 门禁修改无效，回退。

### 4.6 期望值必须来自被测实现之外（第 38 条）

同一条 check 的期望值不得由**被测实现的同一个函数**现算，否则断言只证明「接线把 A 算成 A」，不证明公式正确。

- **必须至少有一处独立来源**：手算常量（AC 例值）、恒等式（成本恒价时浮盈亏恒为 0；`市值 = 最新价 × 数量` 的双路径复算）、或用另一条独立实现路径交叉验证。
- **允许的写法和不允许的写法**：`expect = positionTexts(1500, 100, 1682.4)` 与实现共用函数 → 只能算**渲染接线**证据，必须单独标注 `oracle=derived`；同一 AC 必须另有 `oracle=independent` 的 check（手算常量），两者不得相互替代。
- **适用范围**：取证脚本（`*Diag.ts`）、门禁自测（`verify_*_selftest.mjs`）、单测断言一视同仁。工具自测若用被测函数生成期望值，selftest 结论作废。
- **判定**：交付说明必须列出每条 AC 的 `oracle` 类型；只有 `derived` 没有 `independent` 的 AC 记 `待补`，不得计入该 AC 的通过证据；签字时 TL 抽查。已在账上的同类写法按第 34 条不追溯，但**本次 diff 触碰到的 Diag/门禁脚本必须按本条重扫**。
- **已知实例**：`P10-R5`–`P10-R8` 用 `positionTexts()` 现算期望值 → 只算渲染接线；公式独立数字只有 `P10-R2`/`P10-R3`。P10 签字按此记，不把 R5–R8 当公式证据。
- **不合格判定**：一条 AC 的期望值全部来自同源实现、且无独立数字 → 该 AC 证据无效；用同源 oracle 冒充独立证据 → 按「伪造证据」处理。

### 4.7 取证套件首次进入合并前必须由非作者真跑（第 39 条）

套件在首次进入合并前，必须由**非作者**（BA 或另一名 dev）在干净 tip 上真跑一次，并记录 `suite`、`commit`、结果与失败列表。未记录「首次真跑」的套件不得合并。

- **理由**：判据写的是行为，套件写的是**对被测实现的隐含假设**；两者不一致时，只有真跑会暴露，静态审查看不出来。
- **反例（真实）**：`s080202` 假定 `setInject("panic")` 常驻，实现 `take_inject()` 消费一次即回落；该套件此前从未被真跑，一直躺在「待验收」，进入取证后第 2 次重试超时、整包 240s 无 dump。
- **判定**：无「首次真跑」记录 → 该卡不得合并；记录造假 → 按伪造证据处理。
- **与第 34 条关系**：本条只约束**进入合并**的套件，不追溯已签证据。

### 4.2 汇总口径

顶层汇总必须覆盖所有 `verification` 子块（第 30 条），`ok = checksOk && verificationOk`；任一子块 `ok=false` 顶层即 false。禁止用 `checks[]` 的全绿掩盖子块红。

### 4.3 工具与检查器

- 检查器不算交付，除非：有反例、有 selftest、进 CI、且**工具开发者不得做该工具的取证执行人**（§6）。
- `dom-contracts.json` 为选择器唯一清单（第 32 条）；新增 `data-*` 不登记即红。

### 4.4 不合格判定

缺反例 = 未交付；反例不能变红 = 检查器无效，工单退回；变异后反例仍红 = 反例与被测逻辑无关，退回。

## 5. 合并前置

1. `main` 工作区干净、已 push、CI 在 tip 上跑过。
2. 对待并入 diff 先跑 `npm run verify:sign-impact -- --staged` 预演（不是合并后再补）。
3. 共用文件（`app/bench`、`app/manifest/indicators.json`、`app/scripts/dom-contracts.json`）**先合先定基线**；后合一方按基线重生成，禁止各改一处。
4. 合并后必须重跑 `verify:evidence`、`verify:dom-contracts`、`verify:gate-log`、`verify:sign`；两边各自的绿拼起来可能是红的。
5. **不合格判定**：`verify:sign-impact` 白名单外命中非 0、或合并后任一 `verify:*` 红，即不得合并；已合并的按第 21 条处理。

### 5.5 逐卡交付：完成一张、验证一张、合并一张

- 以**卡**为单位，不凑批次、不排窗口、不等整点。dev 完成一张即交 BA；BA 验过即合 `main`；合并后 dev 立即取下一张。
- **证据必须能重跑**：`evidence-run.sh` 在干净树或独立 worktree 上产出，`commit` 真实、`dirty=false`；手工快照、`diag-evidence.sh` 产物不作证据。今天差点拿手工快照签，这条不放宽。
- **交付以「远端可达的 SHA」为准**：只有 `origin` 上可达的提交才算交付，**本地分支领先远端再多也等于没做**。报完成必须给远端分支名 + SHA，BA 从远端取 tip 验证，不得从本地对象库取一个远端没有的 SHA。2026-11-08 两次「等 BA 结论 / 等合并」各耗数小时，根因都是提交压根没推。
- **取证环境瞬时抖动**：`windowFocused=false` 允许**原样重跑一次**；重跑为 `true` 即判通过，并在 `note` 写「首次焦点丢失、重跑通过」。**不许改字段、不许补值**；两次都 `false` 才算不可判定、不签。已知诱因：Electron 宿主抢前台约 2 秒，属环境抖动，不记产品缺陷。
- **一卡一个 tip**：证据的 `commit`、断言所在代码、合并记录指向同一 SHA（或证据 commit 为合并 commit 的祖先，且期间无该卡相关文件改动）。禁止「证据在 A、合并记 B」。
- **断言必须能红**：每卡至少一处独立期望值 + 一条能让它变红的反例/变异；全绿但 AC 零覆盖 = 不合格。今天被推翻的卡就是 checks 全绿、4 条 AC 零覆盖。
- **合并记录**：合并时由门禁在 `gate-log` 写 `sign_commit`（合并 SHA）、证据文件名、验证人（BA）、CI run。这是**自动记录**，不是独立排期事件，不占时间。
- **失败只退单卡**：某卡证据不过，该卡回池重修；其他卡照常合。
- **不合格判定**：证据不可重跑、一卡两 tip、或无红例 → 不得合并；已合入按第 21 条回退。

### 5.6 状态冻结：只冻结在制卡的相关文件

- 冻结点：某卡从**开始采集证据**到**合并完成**；只冻结该卡相关文件——其 diag 源、套件脚本、证据文件、`gate-log` 该行。
- 其他卡、其他目录照常合并；**不再有全局 `app/` 冻结，也不再按日期冻结**。
- 采集必须在干净树或独立 worktree 上进行，`git status --porcelain` 为空；采集后该卡相关文件若有变动，证据作废重采。
- **不合格判定**：采集时 `dirty=true`、或证据 commit 之后相关文件被改动且未重采 → 本次证据作废。

### 5.7 页面注册表由 BA 单一维护

- `docs/qa/aka-page-registry-v0.1.csv` 属台账，**只由 BA 写**；`status`、`anchor_file`、`anchor_text` 三列不得由 dev 改动。
- dev 交付页面或生成器时，只提供锚点三件套（`page_id`、`anchor_file`、`anchor_text`），写进工单或提交说明；`exists` 的判定由 BA 在合并后跑 `verify:docs`（含 `verify:card-pages`）命中锚点再落表。
- 合并方合入 dev 批次时**剥离该文件的改动**；注册表作为独立 `docs(qa)` 提交，不与代码混在同一提交。
- 理由：`exists` 是页面层门禁结论，dev 自己写等于自证交付；且与 dev 不得改台账/签字的既有分工一致（§6）。
- **不合格判定**：dev 提交含注册表三列改动 → 合并前剥离；已合入的恢复至合入前状态，由 BA 重写。

### 5.8 卡池不断供

- 每个 dev 手上始终有下一张卡：交付一张后**立即取下一张**，不等合并、不等验证结果、不等通知。
- 在制卡数固定为 1；从交付到取卡不超过 **10 分钟**。
- 池空是排期问题，TL 当天补卡或拆卡解决，不得让 dev 停工。
- **派单前先读 §0.0**：以工单 §0.0 为唯一派单真源。§0.0 里没有的卡，**先写入再派**；已写入的，按 owner 与状态判是否已被占用。
- **每行必须有「最后核对 commit」**：池子每行记 `last_check`（最近一次核对时的 main commit）。**核对以 main 实际代码为准，不以 CSV 历史状态为准**。
- **过期不得直接派**：`last_check` 超过 **24 小时**，或 main 在该次核对后又合并过**任一提交**，该行即过期，派单前必须重核；未重核的卡不得派。
- **禁止各持一份局部状态**：不得凭记忆或本地清单派单。两人各记一份，重复派单必复发，代价是两份改动互相覆盖（第 35 条）。
- **不合格判定**：dev 因无卡空闲超过 10 分钟 → 记排期事故，当天补位；同一张卡派给两人 → 记重复派单事故，保留先派方，后派方立即撤回并改派池中下一张，且 §0.0 标注「曾重复派单，已切开」；派出未核对的过期行 → 记派单事故，撤回并重核。
- **工具卡硬上限**：产品卡可开工数为 0 时，**最多一人做工具/门禁卡**，另一人做「解阻」——核卡面、补套件入口、补齐缺的断言，为产品卡进入 main 清障。不得两人同时陷在门禁工程里。
  - 理由：**门禁的价值是让产品能进 main，不是让门禁自己变完整。**

### 5.9 停滞判据（自动轮询）

- 判停滞三选一：**45 分钟无新回合**（锚为最后一次回合/提交/文件写入三者最新）；工作区有未提交改动、无更新的编译/测试产物、且无回报；回合结束但结论含糊（没有完成/阻塞/下一步）。
- 编译或测试进程在跑、产物在推进 → 不算停滞，不打断。
- 首次停滞：只问三件——**到哪一步、下一步、有无具体阻塞**；不要求写进度说明。
- 连续两轮停滞：升级上报，附时间戳、进程状态、`git status`。
- 第三轮停滞：停任务、重排。
- 轮询只读、不写仓；目的是解阻，不是收汇报。

### 5.10 写作与取证分树

- **写 `docs/` 必须去独立 worktree 或独立克隆，写完推分支**；`main` 主树只用于合并与取证，不承载任何人的在制编辑。
- 原因：写作者与取证者共用一棵树，而取证第一道门是「干净」。**只要写作在主树上进行，BA 必然被卡**——这是结构冲突，不靠「记得提交」解决。
- 不合格判定：主树出现未提交改动且 BA 正在取证 → 记取证阻塞事故；写作留在主树过夜或过下一回合 → 记流程事故。
- 例外：TL 在 `main` 上做合并/回填 `gate-log` 时，必须一次编辑、立即提交，窗口内不得夹带其他写入。

| 角色 | 可以做 | 不得做 |

## 7. 状态同步义务

- **查表与派单只读 `origin/main`**：查状态表、派单、贴单前必须先 `git fetch origin`，再读 `git show origin/main:docs/qa/aka-card-workorder-v0.1.md`；不得以本地工作区副本为准（这是 W-92 的同一机理：写了但没同步，三份副本三张表）。本地副本只作编辑缓冲，提交推送后以 `origin/main` 为准。
- `docs/qa/aka-card-workorder-v0.1.md` §0.0 是唯一共享状态表。**取卡、开工、报完成、停线当天写入**；别人贴单前先看它。
- 每行必须带 `更新日`（`YYYY-MM-DD`）。进行中必须写分支/worktree；停线必须写原因与恢复条件。
- **「当天」怎么判**：判定人 TL；时点 = 派单前看一次、贴单前看一次、批次边界复核一次。机器只保证日期自洽：格式合法、不晚于今天、行内有 commit 时 `更新日` 不得早于该 commit 的提交日。机器证不了「事件发生在当天」，倒填由 TL 发现即该行状态作废，按未开工处理。
- 每天至少一次由 TL 对表；批次边界统一复核（第 14 条）。
- **不合格判定**：`verify:delivery` 校验状态表（重复编号、非法状态、进行中缺分支、表内编号无对应工单标题、`更新日` 缺失/格式错/早于 commit 日），并校验本地 HEAD 不得落后 `origin/main`（落后即红，提示先 fetch/rebase 再查表）；缺一项红。人工判定：聊天里说「在做了」但表里没有 → 视为未开工；倒填日期 → 该行作废。

## 8. 汇报节奏

### 8.1 必须立刻报

- 取证失败、崩溃、超时、零 dump；
- 阻塞（依赖未交付、环境不可用、权限缺失）；
- 需要口径裁定（状态词、卡级取严、签不签）；
- 发现已签证据被推翻（实质反证）。

### 8.2 可以攒到批次边界

- 交付进度、下一批计划、非阻断 WARN、时延观察值（如 `b2Render 291ms`）。

### 8.3 汇报格式

- 结论 + 数字 + 口径 + 证据路径/commit。禁止「基本可签」「建议放行」「除某条待定」。
- 计数必须双口径（第 22 条）：卡数/人日百分比分开写。
- **不合格判定**：评审。缺口径、缺 commit、用模糊措辞，汇报退回重写。
