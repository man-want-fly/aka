## 4. 两个方案的利弊

### 方案 A：只展示已实现（PRD 现行）

**做法**：目录/抽屉只渲染 `implemented=true` 的项；现在 44，GA 84；页头 `44 个`。

利：
- 零死链：每一行都能加、能改参、能看口径，「专业感」来自「都能用」。
- 与 PRD 现有 AC 一致，不用改 PRD；与 D-05「每个可见指标都能画线」一致。
- 实现最省：不需要 `status/completeness/is_completion` 之外的规划态样式，也不需要灰行。

弊：
- **目录单薄**：MVP 阶段只有 44 行，6 类里量能、广度为 0，分类头会出现「该分类暂无指标」，第一眼像「指标库没做完」。
- 「105 个」的品牌承诺无法传达；用户无法确认「有没有 DMI/ADX」这类「以后会不会有」的问题（正是 S-03.01-01 卡里写的角色场景）。
- 与卡 AC 冲突：AC-03.01-01「105 行」、AC-02.04-01「合计 105」全部判不通过，除非改卡。

### 方案 B：展示 105 条（含置灰）

**做法**：全量 105 行，44 可用 + 61 置灰「规划中」；P1 21 条另标 `P1`。

利：
- 「指标库」体量与分类覆盖第一眼成立，6 类都有内容，符合卡 AC 与 D-05 的 105 个 id。
- 用户能回答「有没有某指标」；未来上线时不用改信息架构。

弊：
- **MVP 阶段 58%（61/105）是灰的**，观感像「半成品」；比「只有 44 个但都能用」更容易被判「没做完」。
- 死链风险：用户点灰行 →「本期未开放」；点一次可忍，连续遇到 3–4 次就会怀疑整个库都不可用。
- 标签真实性：61 条里只有 21 条是 P1，另外 40 条是「P0 但尚未实现」。若统一标 `P1`/「后续开放」是说谎；必须区分「规划中（P0 未实现）」与「P1 后续开放」，否则口径页/目录会自相矛盾。
- 与 PRD D-05「不得以占位行出现在目录」直接冲突，必须改 PRD；改完还要处理「每个可见指标都能画线」这句。

### 改造成本（相对现有实现，BA 估）

| 方案 | 要做的事 | 增量 | 代价 |
|---|---|---|---|
| A 只展示已实现 | 无 UI 增量；但要重写 3 张卡的 AC（105 → 44/84），并删掉卡里的 P1 灰行/徽标要求 | 0 人日（文档返工） | 「105」承诺落空，目录 44 行 |
| B 展示 105（含灰） | 灰行样式与徽标卡上已有；补 61 条 `status`、默认 105 行滚动性能、P1 拒绝提示 | +0.5 人日 | 58% 灰行，死链感 |
| C 分层展示 | 类尾折叠入口 + 搜索「另有 N 个未上线」提示 + 双数计数 | +1.0–1.5 人日 | 需改 PRD + 2 条卡 AC + 1 句 Conversation |

### 观感代价比较（哪个更高）

**「点了不能用」的代价更高。** 理由：

1. 死链是**信任问题**：一次「+ 副图」被拒，用户会把「105 个」重新理解为「一堆不能用」，之后连可用的 44 个也不敢点。单薄只是**体量问题**，不会让人怀疑功能真假。
2. 灰行占比 58% 时，产品更像「路线图」而不是「工具」；而 v0.1 的定位是单机可用的分析工作台，首屏应给「现在能做什么」。
3. PRD 自己把「无占位行」「每个可见指标都能画线」写成硬约束，说明产品意图本来就是「所见即能用」；卡上的 105 行是**信息完整性**诉求，不是「必须让用户点灰行」。

关键约束：**灰行如果只能弹一句「本期未开放」，就没有真正的落点。** 卡上给的落点是「P1 可点进口径页」，但口径页要 84 页（P1 那 21 条不在其中），MVP 阶段没有内容可落。于是：

- 方案 B 在 MVP 的真实形态 = 61 条灰行 + 一句拒绝提示 = 死链；
- 方案 A 没有死链，但只剩 44 行；
- 要让「105 可看」和「零死链」同时成立，只能让**默认视图不含灰行**，灰行退到可展开的信息层——这就是方案 C。

因此：**不能为了体量把 61 个死链堆到默认视图里**；但也不必把 105 藏起来——用「折叠/分层」把「能用的」和「规划中的」分开即可。

## 5. 第三种折中（推荐）：同一份 105 注册表，两个视图不同默认

### 5.1 规则

| 位置 | 默认视图 | 105 的呈现 | 计数 |
|---|---|---|---|
| P3 指标目录 `S-03.01-01` | 6 类全部展开，**只列可用（implemented）行** | 每类头 `可用 4/24`；类尾一行「另有 20 个规划中 · 展开」；展开后显示灰行（名称+缩写+`主图/副图`+「规划中」tooltip），**无「加入」「查看口径」按钮** | 页头 `44 可用 · 共 105 规划`（GA：`84 可用 · 21 后续开放`） |
| P2 指标抽屉 `S-02.04-01` | **只列可用行**，默认分类同上 | 不展示灰行 | 分类头 `4/24`；页头 `44 可用` |
| 搜索 `S-03.01-02` / 抽屉搜索 | **只搜可用行** | 命中规划项时，在结果末尾追加一行提示「另有 N 个未上线指标匹配「xxx」· 查看清单」（不可添加） | `找到 N 个可用` |
| 105 元数据 | 全量存在，`status` 区分 `p0-implemented` / `p0-planned` / `p1-planned` | 供展开与提示使用 | — |

### 5.2 为什么这是折中而不是新方案

- 它保留方案 B 的「105 可查、可数、可展开」，所以 `S-03.01-01` 的「用户要知道以后会有什么」成立；
- 它保留方案 A 的「默认所见即能用」，所以 `S-02.04-01` 的「P1 不可添加」不会变成高频死链；
- 开发现在按「44 可选 + 61 置灰」实现也不用返工：**只要灰行默认折叠、只在目录展开后出现、抽屉不出现**，再加一行搜索提示即可。
- 61 条逐步上线时，灰行自动变可用、计数自动从 `44 可用 / 105` 走向 `84 可用 / 21 后续开放`，不需要改布局。

### 5.3 代价

- 需要改 3 处 PRD 表述（D-05、F-03.01、AC-03.01-01/AC-02.04-01）与 2 条卡 AC 的计数口径（单值 105 → `可用/总数` 双数）。
- 还需要改 `S-03.01-01` 的 Conversation「不按 P0/P1 折叠、全部列出」一句，并统一卡内「默认收起 / 默认全部展开」的矛盾（建议：**分类默认展开、规划项默认收起**）。
- C 下灰行不再提供「查看口径」：MVP 阶段 61 条没有口径页内容，点了只会是空页；这同时改动了 `S-03.01-02`「P1 可点进口径页」与 `S-03.01-01` 行内「查看口径」按钮的适用条件（仅可用行）。
- 目录默认仍是 44 行，**单薄问题只缓解不消失**；靠「类尾规划入口 + 页头 105」传达体量。
- 增量约 1.0–1.5 人日（折叠入口 + 搜索提示 + 双数计数），低于返工成本。

### 5.4 推荐

**推荐方案 C（分层展示：目录可展开看 105，抽屉/搜索只用可用项，计数统一为「可用/总数」）。**

一句话理由：它把「能用的」放在默认路径、把「会有的」放进可展开的信息层，同时消除死链与单薄两种代价，且 61 条上线过程中零返工。

## 7. 对开发的落地约束（不改现状实现也可满足）

1. 灰行**只在目录页、且用户点开某分类末尾的「规划中 N」入口后**出现；抽屉与搜索结果**永不出现灰行**。
2. 灰行不给「加入图表」「查看口径」按钮，只给 tooltip「规划中 · 本期未实现 / 后续开放」。
3. 所有计数改成双数：`可用 N / 共 M`；搜索页头写 `找到 N 个可用`，无结果文案沿用 `S-08.01-02` 的「仅搜索已实现 {M} 个（共 {T} 个）」。
4. 抽屉与目录搜索共用同一函数、同一防抖（建议 150ms）与同一五级优先级；两卡现有的 200ms/150ms、四级/五级差异按本节统一。
5. 注册表字段先补 `abbr`、`pinyin_initials`、`panel`、`formula_summary`、`status`、`completeness`、`is_completion`、`default_params`；缺一项，方案 C 的分类头/灰行/tooltip 都做不实。

## 7A. 最终落地口径（v0.3，替代 §5 方案 C 的推荐）

> §5 推荐的方案 C（「抽屉/搜索不出现规划项，灰行折叠进目录类尾」）**未被采纳**。实际落地为方案 B 的强化版：**105 条全部可见、可搜、置灰、不可添加**，并用「双轴」把「公式写完没有」与「依据从哪来」分开。以下为准。

### 7A.1 双轴语义（与 PRD D-24a 同源）

| 轴 | 字段 | 回答的问题 | 用途 | 当前分布 |
|---|---|---|---|---|
| 完备度 | `completeness` | 公式**写完了没有** | **数值验收基线**（发布门槛与黄金用例范围） | 完整 78 / 部分 19 / beta 8 |
| 溯源 | `specStatus` | 依据**从哪来** | 溯源与用户提示，**不参与验收分层** | `manualComplete` 88 / `partial` 13 / `productDefined` 4 |

两条硬规则：

1. **不得互相代偿**：不能用 `completeness=beta` 表示「手册没覆盖」——那会把完整数从 78 降到 65，推翻 D-24；也不能用 `specStatus=partial` 表示「公式没写完」。
2. **两轴各自渲染**：同一行可以同时出现两个徽标（如 M22 同时 `beta` + `口径待定`），tooltip 不得合并成一句。

### 7A.2 用户可见徽标（进入 P1 开发前必须能区分）
