0. 一句话结论

AKA 是一个单进程、双宿主（WebView UI + Rust 计算）的 macOS 应用：UI 与计算之间只有一条类型化的 Tauri IPC 边界；数据只落在本机 state.db 与 data/sim；MVP 不发起任何网络请求，外部数据源与更新通道只是预留边界，诊断包是唯一会离开本机的产物，且由用户手动导出。

骨架期差异：首版骨架的 mock 行情在进程内生成、只保存在内存 CandleStore，尚未创建 state.db / data/sim；Parquet + SQLite 按本图规划在后续 Sprint 落地。

部署红线：没有 Python、没有 sidecar、没有本地 HTTP 端口、没有云端账号体系。安装包即全部运行时；断网可完成「首装 → 行情 → 工作台 → 指标改参」全链路。

2. 部署单元与运行时职责

部署单元形态职责MVP 边界
AKA.app单个 macOS 应用包（arm64 + x86_64）WebView 宿主、Rust 主进程、本地数据目录、菜单与窗口签名 + 公证后分发；无 helper / 无 sidecar / 无 XPC 服务

更新通道签名 dmg + 更新清单版本分发与升级MVP 关闭，不检查更新；后续再引入签名校验
诊断包本地 zip，用户手动导出排障与反馈唯一会离开本机的产物；不含行情数据与自选代码

3. 上下文边界与不可变约束

进程内边界

  • UI ↔ Rust：只有 Tauri IPC；命令名与请求/响应形状在模块架构图第 3 节列出。
  • app-core ↔ 计算：indicator-core 只吃切片，不认识 Arrow、tokio、SQLite、provider。
  • app-core ↔ 数据：data-provider 产出源模型，data-store 只存归一化后的列式数据；两者互不依赖。
  • 反向依赖禁止：indicator-core / data-provider / data-store 不得依赖 app-core 或 aka-desktop。

进程外边界

  • 外部数据源：MVP 不联网；tushare 只保留请求构造与响应解析，传输层由 feature = "live-tushare" 控制。
  • 更新通道：MVP 不检查更新；未来采用签名 dmg + 公证，更新前校验签名与版本单调。
  • 诊断包：本地生成、用户手动发送；排除行情原始数据、自选代码、持仓成本。
  • 无云控制面：无账户、无登录、无支付、无订阅、无遥测上传。
范围守门：任何「云同步、账户、支付、自动更新、实时行情」需求都必须先改 PRD 的冻结决策（D-02 / D-09 / D-10），不能在实现阶段悄悄塞进架构。
